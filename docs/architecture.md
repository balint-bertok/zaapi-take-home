# Architecture

Answers: how does the system work, what must always hold, and what has already been rejected?

## Flow

A static single-page app (ADR 0001). No backend, no network: every click changes in-browser state only.

- **Routes.** Each feature folder (`src/features/auth`, `tickets`, `ai`, `automations`, `settings`) exports its own `routes.tsx`, a list of `AppRoute` (`path`, `title`, `layout`, lazily loaded `Page`). `src/routes.tsx` only concatenates them; it is the one route table, and the invariant suites walk it. `src/App.tsx` groups the table into layout routes by `layout`, sets `document.title` from the route (titles from the catalog's `seo.metaTitle`, in `src/lib/route.ts`), and sends `/` and any unknown URL to `/login`.
- **Shell.** `layout: "auth"` pages stand alone. Every other page sits under `AppLayout` (`src/shell/`), the free-trial banner. `layout: "canvas"` (Flow Builder) gets the banner only; a section key (`tickets`, `ai`, `automations`, `settings`) also gets `ShellLayout`: the icon rail, that section's sidebar (`src/shell/sections.ts`, labels from the English catalog) and the content card, mounted once per section so navigation swaps only the card's contents. Inside the card a page renders `<ShellPage breadcrumb>` (header plus the standard page container) or fills the card itself. Tickets is the one exception to the section layout: its menu carries per-entry icons and live counts, so `/tickets` takes `layout: "canvas"` and `TicketsPage` composes the rail, its own `TicketsSidebar` (labels and links still from `sections.ts`) and the card; `?inbox=closed` and `?ticketId=` are read by the same page (the Closed entry itself is inert, user decision 2026-10-02). `layout: "setup"` is the guided setup of the first AI Agent (`src/features/setup/`): the section frame with the AI Agent rail entry current and a step list (`SetupSidebar`) in place of the section menu; until the store's `agentLive` is set, the rail's AI Agent entry leads there and every section but Tickets is inert. Anything that looks clickable but leads to an uncaptured page renders through `<Inert>` (`src/components/Inert.tsx`).
- **Look.** `src/index.css` holds the real app's theme tokens and base rules verbatim. Icons come from `src/icons/registry.ts`, generated by `scripts/extract-icons.mjs` from the saved pages. Inter is served from `public/fonts/`. Brand, channel and customer images live in `public/images/`; reference them through `asset()` (`src/lib/asset.ts`) so the Pages base path is applied.
- **Store.** `src/store/store.ts` keeps one `DemoState`, seeded from `src/store/fixtures.ts` (shared state plus one slice per feature from `src/features/<name>/fixtures.ts`) and persisted to one localStorage key. Read with `useDemo(selector)`, write with `updateDemo(current => next)`. `?reset=1` on any URL restores the fixtures.
- **Build and deploy.** `npm run build` type-checks, builds to `dist/` under the `/zaapi-take-home/` base path and copies `index.html` to `404.html` so Pages serves deep links. `.github/workflows/pages.yml` publishes `dist/` after the ci gate passes on a push to `main`; the squash merge is the release. Pages answers deep links from `404.html`, so they render correctly but carry HTTP status 404 (a static host has no rewrite rules); the route walk checks status against `vite preview`. Public URL: `docs/third-parties.md`.

## Non-negotiable invariants

Each has one suite in `docs/testing.md` and is never weakened to make a feature pass; renegotiate with the user.

1. **No outbound network.** The built demo requests nothing from any host but its own origin: no CDN fonts, no analytics, no API.
2. **Every route renders.** Every route in the table answers 200, renders with no console error or uncaught exception, carries its catalog title, and links only to routes in the table.
3. **No secret reaches git or output.** Gitleaks over the full history (pre-commit hook, `scripts/gate`, CI), plus a test that `.env` stays git-ignored and that `src/`, which ships to a public page, holds no credential-shaped literal.

## Roadmap

From the validated plan (`Original files/extracted/PLAN.md`), one PR each:

- PR 0, scaffold and shell.
- PR 1, auth and onboarding: register, verify-email redirect, login, onboarding modals, get-started card. Built.
- PR 2, tickets: inbox sidebar, ticket list, conversation pane, contact panel. Built.
- PR 3, AI Agent: knowledge source, scenario handling, personality, test chat; Deploy and Analyse stay inert. Built.
- PR 4, automations: basic automations list, template picker, assign-to-agents form. Built.
- PR 5, flow builder: flow list, template gallery, React Flow canvas (`@xyflow/react`, its stock stylesheet plus the app's one override), publish dialog; flows live in the `flows` slice. Built.
- PR 6, settings: settings sidebar, billing page. Built.
- PR 7, fidelity pass against the live app. Built; differences and waivers in `docs/fidelity.md`.
- Prefilled login: register and login open with fake demo credentials (`src/features/auth/demoCredentials.ts`), so one click on "Get started" or "Log in" lands on `/tickets`; `/register/verify` stays routable but leaves the click path (user decision, 2026-10-02). Built.
- Prefilled onboarding: the first onboarding modal opens with the store's demo user as the name and a staff count from `src/features/auth/demoCredentials.ts`, so Continue is enabled on arrival; both stay editable (user decision, 2026-10-02). Built.
- Guided setup path: intro, persona, scenarios, knowledge, test, go live, each form state its own route under `/ai/setup`, the dashboard gated until go-live (ADR 0002). The first four steps run in a modal over the setup page, test and go live stay pages (ADR 0002 amendment). The done page can reset the demo and return to sign-up, so the journey loops (user decision, 2026-10-03). Built.

PRs 1 to 6 run in parallel after PR 0 merges; each touches only its own feature folder.

## Alternatives considered: don't relitigate without new facts

| Rejected | Why | Date | Whose decision |
|---|---|---|---|
| Backend, database, cloud or VPS deployment of any kind | Out of scope for this take-home; front-end only, GitHub is the only destination | 2026-10-01 | User |
| Next.js static export | Heavier, no fidelity gain over Vite (ADR 0001) | 2026-10-01 | Session, on the user's stack-agnostic brief |
| Lucide or any other icon library | The user wants identical glyphs; icons are extracted from the saved pages | 2026-10-01 | User |
| Live capture of pages that were never screenshotted | Dropped | 2026-10-01 | User |
| Building pages without a screenshot (Analytics, Broadcast, Contacts, Notifications, Search, AI Deploy and Analyse, Settings other than Billing) | Pages without screenshots are not built; their entry points render but are inert | 2026-10-01 | User |
